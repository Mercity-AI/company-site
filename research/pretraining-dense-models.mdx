We pretrained a set of dense **1-billion-parameter** checkpoints from scratch on **6B** [FineWeb](https://huggingface.co/datasets/HuggingFaceFW/fineweb) tokens, then used them to test ideas that were validated on larger-scale sparse MoE models: Kimi Delta Attention (KDA) from [Kimi K3](https://arxiv.org/abs/2607.24653), and the [LongCat n-gram embedding module](https://arxiv.org/abs/2601.21204). Each went in as a single-variable ablation against a shared baseline. We then grafted modules between checkpoints, pruned whole layers, quantized each model to 4-bit, and fine-tuned the baseline and n-gram checkpoints on a downstream NER task.

**Results at a glance:** We found that a well-tuned dense baseline is the model to beat at this scale, and neither imported idea clearly beats it. KDA matches it (**41.37** vs **41.23** Shared-9, within single-seed noise). The n-gram tables give up transformer depth for embedding capacity and lose on both fronts: **0.7** and **1.7** Shared-9 points behind on the benchmarks, and **3** and **6** points of NER micro-F1 behind after fine-tuning. Adding QK normalization to the baseline erased KDA's earlier lead.

The sections below follow the order we ran the experiments: pretraining first, then the downstream and diagnostic experiments.

The code is on [GitHub](https://github.com/Mercity-AI/MoE-Runs) and the pretrained checkpoints are on [Hugging Face](https://huggingface.co/collections/Mercity/pretrain-checkpoints).

## Why do this?

New architecture ideas keep arriving from frontier labs, and they are almost always validated on very large models: wide, sparse, and trained on tens of billions of tokens or more. We wanted to know how these state-of-the-art techniques behave when you train a small language model instead, with an academic token budget and a single GPU. To test that, we picked two recent examples: Kimi Delta Attention (KDA), a linear-attention layer introduced in [Kimi Linear](https://arxiv.org/abs/2510.26692) and used in the [Kimi K3](https://arxiv.org/abs/2607.24653) mixture-of-experts model, and the [LongCat n-gram embedding tables](https://arxiv.org/abs/2601.21204), reported on **20B to 60B** parameter models. We have not found published results for either on a dense model near 1B parameters, so these runs report new numbers.

## What did we do?

> **TL;DR:** Our four checkpoints share a common Llama 3 + QK-norm backbone, each trained on **6B** FineWeb tokens with Muon and AdamW, on **8,192**-token sequences packed from FineWeb documents. For the training stack we used a single NVIDIA B200 with FlashAttention 4 and Liger kernels (SwiGLU, RMSNorm, and fused linear cross-entropy), with TorchTitan running the training loop.

All four models share the same backbone: a Llama3-style dense decoder with grouped-query attention, RMSNorm, SwiGLU MLPs, and tied embeddings. We use the [Llama 2 tokenizer](https://huggingface.co/meta-llama/Llama-2-7b-hf) with a **32,000**-token vocabulary to keep the models English-only. The four pretrained checkpoints differ only in the one component under test, so any benchmark gap traces back to that component and not to a change in width, tokenizer, or data.

The four checkpoints are:

1. **Baseline**, the plain dense backbone with QK normalization on.
2. **KDA**, which swaps a quarter of the attention layers for Kimi Delta Attention.
3. **N-gram 25%**, which spends about a quarter of its parameter budget on LongCat n-gram tables.
4. **N-gram 50%**, which spends about half its budget on those tables.

All four land near **1.03B** total parameters. That equal-budget framing is what makes the comparison fair. The n-gram models buy embedding tables by giving up transformer depth, and KDA replaces attention layers rather than adding parameters, so every model spends the same budget a different way.

### The variants

Both ideas change a part of the transformer most readers already know well: KDA changes attention, and the n-gram tables change the input embedding. For each one, we first explain what it is and the extra vocabulary it brings, then how we set it up in our models.

#### Kimi Delta Attention (KDA)

Softmax attention compares every token against every earlier token. That is what makes it powerful, but its cost grows quadratically with sequence length, and the KV cache it reads from grows with every token generated. *Linear attention* swaps the ever-growing KV cache for a fixed-size memory, so cost grows linearly with length and memory stays flat. The catch is that a fixed-size memory fills up, so a linear-attention layer lives or dies by how it writes to that memory and what it forgets. KDA, from Moonshot's [Kimi Linear](https://arxiv.org/abs/2510.26692) work, is a recent answer to that question, and Kimi's models interleave it with a few full-attention layers: three KDA layers for every full-attention layer, so the cheap layers carry most of the depth and the occasional full-attention layer handles exact long-range lookups.

Figure 2 puts the two blocks side by side. Everything outside the attention box is the same; what changes is how each one remembers the past. On the left, softmax attention keeps a KV cache, one key and value per past token, and compares each new query against every entry in it. On the right, KDA replaces the cache with a **state**: a fixed-size matrix, drawn as the grid, that holds a compressed summary of everything seen so far. Each new token updates the state in the four numbered steps, and each step is one of the terms KDA is built from:

- **Short convolution (step 1).** The token's query, key, and value are first mixed with those of the previous few tokens (4 in our models), which gives the layer cheap access to very local context before anything touches the state.
- **Delta rule (steps 2 and 3).** Instead of piling every new key-value association on top of the old ones, the layer first reads what the state already returns for the current key, then writes only the difference, the "delta". A learned **write strength**, β, sets how much of that correction goes in. This is the idea behind [DeltaNet](https://arxiv.org/abs/2406.06484).
- **Forget gate (step 4).** The state also fades a little at every step, so stale information does not pile up. [Gated DeltaNet](https://arxiv.org/abs/2412.06464) uses one fade rate for the whole state; KDA's main change is to give every feature channel its own learned rate, α. That is why each column of the grid is shaded differently: some channels hold on to information for a long time while others turn over quickly.

The query then reads the layer's output from the updated state. Because the state never grows, the cost of each token stays the same however long the sequence gets.

**How we set it up.** Kimi's three-to-one layout makes the network mostly linear, but a mostly-KDA model at 1B and our token budget projected to around **30 hours** on a B200, more than we wanted to spend on a single ablation. So we inverted the ratio and made KDA the *sparse* type. The model is one block of four layers repeated eight times, and a KDA layer opens each block (`kda_every=4`), so **8 of the 32** layers are KDA (layers 0, 4, 8, …, 28) and the other **24** stay GQA (Figure 3). That still answers the question we cared about, how a handful of KDA layers behave inside an otherwise standard dense model, at a cost we could afford. Each KDA layer uses head dimension **128** and a short-convolution window of **4**, as in Kimi's recipe, and we scaled the head count down from the **96** heads Kimi K3 uses to **12**, which keeps the KDA model's total parameters at the baseline's **~1.03B** so the comparison stays budget-fair. The layers run on the chunk-mode kernels from [`flash-linear-attention`](https://github.com/fla-org/flash-linear-attention), which process the sequence in parallel chunks instead of one token at a time, and they L2-normalize their own queries and keys, so the QK normalization discussed below applies only to the softmax layers.

#### LongCat n-gram embedding tables

In a standard transformer, the input embedding looks up one row per token from a table with a row for every entry in the tokenizer's vocabulary (**32,000** rows for us). That row knows nothing about the tokens around it, so working out which words form a phrase is left entirely to the transformer layers. The [LongCat n-gram embedding tables](https://arxiv.org/abs/2601.21204) add a second lookup that does depend on the neighbors. LongCat showed that spending a large share of a big sparse model's parameters on these tables beats spending them on more experts, and because the lookups are cheap and happen only at the input, the tables add parameters without adding meaningful compute per token.

Figure 4 follows one sentence, *"the cat slept on the mat"* (one word per token, for simplicity), into both kinds of model at the moment the model reaches *"mat"*. On the left, a standard model looks up the row for *"mat"* and nothing else. On the right, LongCat makes the same lookup and, in parallel, reads the words around it. Reading the right half from left to right introduces each term:

- **N-grams (the brackets).** An n-gram is a window of the last *n* tokens, and *n* is its *order*. Ending at *"mat"*, the 2-gram (bigram) is *"the mat"* and the 3-gram (trigram) is *"on the mat"*.
- **Hashing (the hash boxes).** There are far too many possible n-grams to give each its own row: with a 32,000-token vocabulary there are about a billion possible bigrams alone. So each n-gram is hashed to a row number. Two different n-grams can land on the same row (a *collision*), so the module sends each n-gram through two different hashes into two tables, which makes it unlikely that two n-grams collide in both.
- **N-gram tables (the tall columns).** Each hash picks one row, the highlighted stripe, and that row's vector is what the model learns about the phrases that land there. The number of rows in a table is its **table vocabulary size**: a bigger table means fewer collisions but more parameters.
- **Projection and LayerNorm (the right edge).** The four looked-up vectors are each projected to the model's hidden size, summed, and scaled by a LayerNorm so the sum sits on the same scale as the token embedding, then added to it.

So before any attention layer runs, the model already sees "mat, as in *on the mat*" rather than "mat" on its own. A model with order-4 tables would also look up *"slept on the mat"*.

**How we set it up.** LongCat's n-gram embedding tables were already shown to help large sparse MoEs, so the open question was where a *dense* 1B model sits on that curve. We put down two points on it. Both variants pay for their tables in transformer depth, and both use two hash tables per n-gram order.

- **N-gram 50%** 6 tables over orders 2, 3, and 4, about **48%** of the parameter budget in tables, **16** transformer layers left (table vocabulary sizes [267003, 367007, 305011, 341013, 345017, 308962]). This reproduces the paper's own setting as closely as a dense model allows, close to the **~46–48%** table share it reports.
- **N-gram 25%** 4 tables over orders 2 and 3 only, about **25%** of the budget, **23** transformer layers left (table vocabulary sizes [144563, 147481, 176677, 180247]). We moved *down* rather than up on purpose: the paper finds the benefit fades past roughly **50%**, so for a small dense model we tested whether a lighter table budget trains more stably, and whether the 50% run's regression was about the depth it gave up.

The second ablation also dropped the order-4 tables, and that was a deliberate call. At 6B tokens the model is heavily undertrained, and a corpus holds far more distinct 4-grams than 2- or 3-grams, so the order-4 tables would see too few examples per row to learn anything useful. That budget buys more when it sharpens the lower orders the model does see enough of. The table sizes and the per-table hash multipliers follow the LongCat paper's recommendations; the full sizing procedure, including the per-order split, is in our internal n-gram sizing report.

| N-gram orders | 2, 3, 4 | 2, 3 |
| Hash tables | 6 (2 per order) | 4 (2 per order) |

A few choices in that table:

- **Tokenizer.** We use the Llama 2 tokenizer and its **32,000**-token vocabulary. It is small and predominantly English, which is what we want. A compact vocabulary spends fewer parameters on the embedding table and keeps the comparison focused on English text rather than multilingual coverage.
- **Near-equal parameter budget.** All four models land within **31M** parameters of each other (**1.006B** to **1.037B**). That is deliberate. The n-gram models pay for their tables by dropping transformer layers, down to **23** and **16** against the baseline's **32**, and KDA swaps attention type without changing the layer count. Any benchmark gap therefore reflects how each model spent the same budget.
- **Training time varies more than the parameter count.** KDA is the slowest at about **18 hours**, because the linear-attention kernels cost more per step than plain attention at this scale. The n-gram models are the fastest, at **10.5** and **13 hours**, because they run fewer transformer layers. The baseline sits in between at **14.5 hours**.
- **Token budget.** We fixed **6B** tokens for every run in this first round. That is about a third of the Chinchilla-optimal **20B** tokens for a 1B model, so every checkpoint is deliberately undertrained. The budget is identical across models, so it does not bias the comparison, but it caps what any single number here can claim, a point we return to in the conclusion.

### Infrastructure and training stack

Every run trained on a single GPU. For each part of the stack we used the newest well-supported tool that was easy to integrate and cut either wall-clock time or memory:

- **[TorchTitan](https://github.com/pytorch/torchtitan)** for the training loop. We wanted the baseline to sit as close to Llama 3.2 1B as possible, and TorchTitan gives that architecture out of the box with strong performance and far less setup friction than DeepSpeed or NeMo. It also kept multi-GPU (FSDP / tensor parallel) available if we ever needed it; we didn't, but the option was free.
- **[Liger kernels](https://github.com/linkedin/Liger-Kernel)**, LinkedIn's open-source Triton kernels for LLM training. Liger provides drop-in fused replacements for the common transformer building blocks (RMSNorm, RoPE, SwiGLU, cross-entropy, and a fused linear cross-entropy that never materializes the full logits tensor), and it is known for cutting training memory sharply while also raising throughput. We used its SwiGLU, RMSNorm, and fused linear cross-entropy (FLCE) kernels. With the freed memory we were able to push the batch size and sequence length up, so every run finished faster on the same token budget.
- **[FlashAttention 4](https://github.com/Dao-AILab/flash-attention)** for the softmax-attention layers. We chose FlashAttention 4 because it is tuned for Blackwell GPUs and for softmax attention layers, which is exactly what our GQA layers are. It matched our hardware (H100 for early tests, B200 for the real runs), gave us a real speedup, and was straightforward to wire in. Its one wrinkle was its GQA packing mode, which broke on our GPUs, so every run trains with it turned off.
- **[flash-linear-attention](https://github.com/fla-org/flash-linear-attention)** for the KDA chunk-mode kernels.
- **NVIDIA B200:** We first ran this exact stack on an H100, and the ETAs came out at multiple days per run. A theoretical throughput analysis showed that a single **180 GB** B200 roughly matches the ETA of a multi-H100 setup at a similar total price, so we moved every pretraining run to one B200. That let us finish the runs faster without setting up distributed training.

Optimizers:

- **[Muon](https://kellerjordan.github.io/posts/muon/)** as the main optimizer for the matrix parameters, chiefly the MLPs. Muon orthogonalizes each momentum update, which conditions the step better for 2D weight matrices and has shown [strong token-efficiency in recent LLM pretraining](https://arxiv.org/abs/2502.16982).
- **[AdamW](https://arxiv.org/abs/1711.05101)** as the auxiliary optimizer for the parameters Muon does not apply cleanly to (embeddings, norms, and biases).

The settings for both optimizers are in the Configurations table above.

> **Regarding torch compile:** We tried `torch.compile` in its various modes, but it kept clashing with the Liger kernels and crashing runs. Most memorably, compiling the fused cross-entropy kernel silently corrupted gradients rather than erroring outright. Even in the configurations we could coax into running, the speedup was marginal, so we left it off.

### Datasets

#### Pretraining data: FineWeb

[FineWeb](https://huggingface.co/datasets/HuggingFaceFW/fineweb) is Hugging Face's large, filtered, deduplicated English web corpus built from Common Crawl. We stream its [`sample-10BT`](https://huggingface.co/datasets/HuggingFaceFW/fineweb/tree/main/sample/10BT) shard, the smallest widely-used FineWeb slice, which is enough to iterate quickly without standing up a heavy data pipeline. We train on **6B** of the shard's roughly **10B** tokens. This was a compute-constraint decision, and we also wanted to understand how these architectures behave at the smallest scale that still gives usable results.

> **Why we pack sequences:** The model trains on fixed **8,192**-token blocks, but most FineWeb documents are far shorter. Putting one document per block would fill most of each block with padding and waste compute on it. Instead we append an end-of-sequence token to each document, concatenate them into one stream, and cut that stream into 8,192-token blocks, so every position is a real token.

Order is randomized with a **10,000**-document streaming shuffle seeded for one epoch. A small, fixed fraction of documents is held out for validation by a stable hash of each document's id, so the train/eval split is deterministic and leak-free.

#### Downstream data: Few-NERD

For the NER fine-tune we use [Few-NERD](https://github.com/thunlp/Few-NERD) ([paper](https://arxiv.org/abs/2105.07464)), a named-entity recognition dataset of about **188,000** Wikipedia sentences, hand-annotated with **8** coarse and **66** fine-grained entity types. It is one of the largest human-annotated NER datasets and a standard reference point in the NER literature. We train and evaluate on its full training and validation splits with random shuffling; more details are in the Downstream NER fine-tuning section below.

## Results

We evaluate the checkpoints in three ways:

- **Base-checkpoint benchmarks.** Nine zero-shot tasks scored on the frozen pretrained weights, our main measure of what pretraining alone wrote into each model.
- **Modifying the checkpoints.** Grafting modules between models, pruning whole layers, and 4-bit quantization: cheap surgeries that probe what the trained weights contain and how they hold up under compression.
- **Downstream NER fine-tuning.** A LoRA fine-tune on named-entity recognition, to see whether the n-gram checkpoints learned anything that carries into a task people actually run.

### The base benchmarks

We score every checkpoint zero-shot (no in-context examples) through the [EleutherAI LM Evaluation Harness](https://github.com/EleutherAI/lm-evaluation-harness) (`lm-eval`), on the full test or validation split of each task with no example cap. Zero-shot keeps the comparison about the weights rather than about prompting, and running the full split removes sampling noise. We report normalized accuracy where the harness computes it (dividing each answer's log-likelihood by its token length, so longer answers are not penalized for length) and raw accuracy otherwise. The headline number is the **Shared-9 average**, the unweighted mean of the nine task scores; since every checkpoint runs the identical suite at the same token budget, these are directly comparable. The nine tasks fall into three groups, by what they probe:

| Group | What the group records | Benchmark | What the model has to do | Metric |
| --- | --- | --- | --- | --- |
| Language modeling and surface statistics | How well the model captures local next-token structure; these move earliest at a small token budget | [LAMBADA](https://arxiv.org/abs/1606.06031) | Predict the exact final word of a passage from its full context | acc |
| | | [HellaSwag](https://arxiv.org/abs/1905.07830) | Pick the natural continuation of a short scene | acc_norm |
| Physical and social commonsense | Whether the model has picked up commonsense relations rather than surface cues | [PIQA](https://arxiv.org/abs/1911.11641) | Choose which of two solutions to an everyday goal is physically sensible | acc_norm |

### The QK-norm lesson

We took the Llama 3 architecture as TorchTitan ships it, and [Llama 3](https://arxiv.org/abs/2407.21783) does not come with QK normalization, so our first baseline trained without it. [Qwen3](https://arxiv.org/abs/2505.09388) does ship with it: take Qwen3's attention, remove QK-norm, and you are most of the way back to Llama 3. The literature is consistent that QK-norm aids training stability (see the [original QK-norm paper](https://arxiv.org/abs/2010.04245) and Stanford's [CS336](https://cs336.stanford.edu)), so we added it to the Llama architecture and reran the baseline. That changed our headline conclusion, because leaving it out had inverted our architecture comparison. It was a major lesson for us: turn QK normalization on every time.

The original baseline converged, but its gradient norm never settled: it stayed high and wavy for the whole run, humping up again through the middle of training. QK normalization (RMSNorm on the query and key vectors before the attention dot-product, which bounds the attention-score scale) fixed it. We added it, changed nothing else, and reran. The two runs follow nearly the same loss path, but the gradient tells them apart: with QK-norm it dropped and stayed flat right after warmup, and its mean over the run fell from **0.58** to **0.20**.

## Modifying the trained checkpoints

Because all four models were trained on near-identical settings and the same data, they are unusually comparable, which let us operate on the trained checkpoints directly: move parts between them, remove layers, and compress them. None of the experiments below needs new pretraining.

Each experiment starts with a hypothesis. We then run it and check whether the hypothesis held, so every section ends with a clear takeaway.

### Grafting

> **Hypothesis:** If what a module learns during pretraining is modular, a module trained in one checkpoint should keep working inside another without retraining: a KDA or GQA module moved into a compatible model at the same layer indices should keep a meaningful share of the recipient's score. The two directions could behave differently, because KDA relies on learned recurrent state, gating, decay, and short-convolution dynamics. The n-gram module sits before the transformer stack, so it should transfer better than either attention module, though not necessarily without loss.

The four models were trained independently but share a hidden size, vocabulary, and tokenizer, and the baseline and KDA models also share a layer count, so a module from one drops into another with no shape mismatch. Grafting asks whether a module that learned its job inside one model still works inside a different one, with no retraining. We ran three transplants:

- **KDA into the baseline.** We copied the **8** KDA layers from the KDA model into the baseline at the same layer indices, replacing the baseline's attention there. This tests whether a linear-attention module trained in its own model can stand in for softmax attention in another.
- **GQA into KDA.** The reverse: we copied the baseline's GQA attention into the KDA model in place of its KDA layers. Running both directions tells us whether any collapse is specific to one donor or a symptom of grafting itself.
- **The n-gram module onto the baseline.** We attached the whole trained n-gram module (tables, projections, and amplification LayerNorm) to the front of the baseline. This is an input-side graft that leaves the transformer stack untouched, so it should transfer more cleanly than an attention swap.

Every grafted checkpoint was evaluated zero-shot on the full nine-task suite with no recovery fine-tuning, so its Shared-9 is a direct measure of how much the transplanted module still functions in its new host.

#### What we found: input modules transfer, attention does not

The two directions of attention grafting collapse almost identically, and the input-side n-gram module survives far better.

### Pruning

> **Hypothesis:** Every trained model leans on some layers far more than others. A cheap screening pass on 500 examples per task suggested that most KDA-containing blocks can be removed one at a time with little loss, and that the earliest blocks, layer 0 in particular, matter most. Re-running every single-block removal on the full suite tests whether that holds.

Which layers are dispensable? We removed one whole decoder block at a time from the KDA model and re-ran the full suite, with a matched control on the dense baseline to separate a KDA-specific effect from plain depth removal.

#### What we found: only the first two layers are essential

## Downstream NER fine-tuning

Benchmarks score the frozen pretrained model. To see whether the pretraining differences survive into a task people actually run, we fine-tuned three checkpoints (baseline, n-gram 25%, n-gram 50%) on named-entity recognition and compared them head to head. NER is a direct test of the n-gram idea: the tables are built to capture short multi-token phrases, so long names, rare words, and heavily fragmented tokens are exactly the cases where they should earn their keep.

> **Hypothesis:** N-gram embeddings are built to capture short multi-token phrases, so the n-gram checkpoints should do better on the NER cases the tables were built for: entities made of long names, rare words, and heavily fragmented tokens. If the 25% model's deficit comes from having fewer transformer layers instead, doubling the table budget to 50% should widen it.

### The data

We use [Few-NERD](https://github.com/thunlp/Few-NERD) with its eight coarse entity types: **person, location, organization, art, product, event, building, and other**. The task is framed as JSON extraction. The model reads a sentence and must emit a JSON list of the entities it contains, each with a type and its exact surface text. Training uses **131,767** sentences; evaluation uses the **18,824**-sentence validation split.

```
Input:  "Miles Davis recorded Kind of Blue in New York."
Target: [{"type": "person",   "text": "Miles Davis"},
         {"type": "art",      "text": "Kind of Blue"},
         {"type": "location", "text": "New York"}]
```

### The recipe

Identical across all three models, so the only variable is the base checkpoint:

| Setting | Value |
| --- | --- |
| Method | [LoRA](https://arxiv.org/abs/2106.09685) on every transformer layer |
| LoRA rank / alpha | 16 / 32 |
| Epochs | 2 |
| Effective batch size | 120 |
| Learning rate | 3e-5, cosine decay, 10% warmup |
| Trainable params (baseline / 25% / 50%) | 16M / 11M / 8M |

The fine-tunes ran on a single RTX 5090 (**32 GB**), using FlashAttention for training and [vLLM](https://github.com/vllm-project/vllm) for inference. LoRA rather than full fine-tuning keeps the run cheap and the comparison about the frozen representations. One limitation it introduces: because LoRA adapts every layer, the shallower n-gram models get proportionally fewer trainable adapter parameters (the **16M / 11M / 8M** above), which we flag where it could matter.

### The scoring

We report on the validation split, running greedy generation over all **18,824** sentences and parsing the JSON each model emits. An entity is correct only when both its type and its exact text match a gold entity, case-insensitively. From that we compute:

- **Micro F1.** Entity-level F1 pooled over every entity in the set, so frequent types dominate.
- **Macro F1.** The mean of the eight per-type F1 scores, weighting each type equally.
- **Sentence accuracy.** The fraction of sentences whose predicted entity set exactly matches the gold set, nothing missed and nothing added.
- **Parse failures.** Answers that do not parse as JSON at all.

These metrics, plus precision, recall, and the per-type breakdown, answer the question the fine-tune exists to ask: did the n-gram checkpoints learn anything that helps them find and label spans of text, or does the pretraining deficit carry through unchanged? Recall and the miss/hallucination split say whether entities are being found at all; precision and the per-type breakdown say whether they are being labeled correctly.

### What we found: the n-gram hypothesis was wrong

Fine-tuning turns the pretraining tie into a clear, statistically significant gap. On Few-NERD the three models line up in strict order, and each **25%** of budget moved from transformer layers into n-gram tables costs a steady **3** points of micro F1.

## Conclusion and limitations

At 1B dense scale on 6B tokens, a well-tuned baseline is the model to beat, and neither imported idea beats it cleanly.

KDA at **8 of 32** layers matches the baseline within single-seed noise. The LongCat n-gram tables reproduce only as a depth-versus-tables trade in which depth wins: they come within **0.67** Shared-9 of the baseline at a compute discount, but against a properly trained baseline they win nothing on the suite (even LAMBADA, the task they target, goes to the baseline), and on a real downstream task they lose everywhere with no compensating strength. The one unambiguous win was QK normalization, which we added after the first baseline run. It fixed training stability and closed almost the entire loss gap to KDA, and it taught us the deepest lesson of the project: an unstable baseline can flip an architecture comparison and make the wrong model look like the winner, so the baseline has to be right before any cross-architecture claim means anything. Among the smaller results, attention is not zero-shot portable, most layers past the second are individually dispensable, and 4-bit compression is close to free.

Each one of these conclusions is limited by the following factors. (1) Each configuration is a single pretraining seed and a single fine-tuning seed, so most gaps outside LAMBADA sit within one to two points of ordinary multiple-choice noise, and we have not measured seed-to-seed variation. (2) The two n-gram variants differ in both table share and layer count at once, so their per-benchmark deltas mix two effects, "tables displace knowledge" and "fewer layers store less", that we cannot separate with these runs alone. (3) The biggest is undertraining: all four models trained on **6B** tokens, roughly a third of the Chinchilla-optimal budget for 1B parameters, and none had flattened when training stopped, so a comparison of undertrained checkpoints can only say so much about how these architectures behave once fully trained.
